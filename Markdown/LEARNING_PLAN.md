# 学習と実装の計画

## 目的と合意した方針

- 今の猫とネズミのブラウザゲームを教材に、複数の人が利用し、記録を共有データベースに蓄積する仕組みを学ぶ。
- 将来の会社用システムに生かせる、データ設計・API・ログイン・権限・運用の理解を目指す。
- 画面は現在のHTML・CSS・JavaScriptを生かす。サーバーはNode.js、データベースはPostgreSQLを使う。
- ブラウザ → サーバー → データベースの流れを、一段階ずつ実装する。
- 初回の保存対象は自分の過去のプレイ記録。その後、利用者ごとの記録へ広げる。
- 学習のため、実装だけでなく初心者向けの解説を必ず添える。
- この文書は計画の記録であり、各段階は実装・確認できた時点で完了に更新する。

## 段階4：利用者を分ける

状態：完了（2026-10-11）

- 利用者の表を追加し、プレイ結果と利用者番号を関連付ける。
- ログインと自分の記録一覧を作る。
- 学ぶこと：表同士の関係、外部キー、認証と権限の違い、ログイン状態の管理。
- 認証には適切な既存のライブラリや仕組みを使う。
- データの所有者は、サーバーがログイン情報から判断する。
- 到達点：2人分のアカウントで、それぞれの記録が正しく保存・表示され、他人の記録を変更できない。
- 実装：`database/stage4.sql` の利用者・セッション表、結果の `user_id` 外部キーと利用者別索引。`scripts/auth.js` と認証API、ブラウザの登録・ログイン・ログアウト画面。
- 認証：Node.js標準のscrypt（N=131072・r=8・p=1）とランダムなソルトでパスワードをハッシュ化。ランダムなCookieと、ハッシュ化したセッション番号をDBで照合。有効期限12時間、HttpOnly・SameSite=Strict、Origin・CSRF確認、認証試行制限。
- 所有者：サーバーがセッションから決め、ランキングを利用者番号で絞り込む。他人のプレイ番号による再送は409で拒否し、元の記録を返さない。記録の変更・削除APIは提供しない。
- 再試行：未送信控えを利用者番号ごとのlocalStorageキーに分離。別タブでCookieが変わっても、画面の利用者番号とCSRFを確認して誤保存・別人の一覧表示を拒否する。
- 既存データ：段階3までの所有者不明の記録は利用者番号NULLのまま保持。旧形式の未送信控えも保持し、新しい利用者へ自動割当・自動送信しない。
- 起動：このPCは `auth-setup` 済み。`node scripts/database.js start`、`node scripts/server.js` を順に実行し、localhost:3000で登録・ログインして遊ぶ。新環境は `npm.cmd ci` と `node scripts/database.js auth-setup`。
- API確認：2人分の保存・取得、8件同時再送、所有者偽装・他人のプレイ番号・CSRF・Origin拒否、入力制約、誤パスワード、名前の重複・大文字小文字、ログアウト・期限切れ、認証試行制限、DB権限、停止・復旧・再起動後の永続化。更新した `tests/stage3.test.js` が成功。
