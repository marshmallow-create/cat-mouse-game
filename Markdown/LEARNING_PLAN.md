# 学習と実装の計画

## 目的と合意した方針

- 今の猫とネズミのブラウザゲームを教材に、複数の人が利用し、記録を共有データベースに蓄積する仕組みを学ぶ。
- 将来の会社用システムに生かせる、データ設計・API・ログイン・権限・運用の理解を目指す。
- 画面は現在のHTML・CSS・JavaScriptを生かす。サーバーはNode.js、データベースはPostgreSQLを使う。
- ブラウザ → サーバー → データベースの流れを、一段階ずつ実装する。
- 初回の保存対象は自分の過去のプレイ記録。その後、利用者ごとの記録へ広げる。
- 学習のため、実装だけでなく初心者向けの解説を必ず添える。
- この文書は計画の記録であり、各段階は実装・確認できた時点で完了に更新する。

## 段階2：データベースを作る

状態：完了（2026-10-08）

- PostgreSQLを用意し、プレイ結果を保存する表を作る。
- 最初は記録番号・スコア・遊んだ日時を保存する。
- 学ぶこと：表・行・列、主キー、SQLでの追加・読み出し・並べ替え。
- 到達点：練習用の記録をSQLで追加し、スコア順で取り出せる。
- 環境：Windows x64用PostgreSQL 18.6を `.local/postgres/` に配置。接続先 `127.0.0.1:5433`、データベース `latte_game`、管理用利用者 `latte_admin`。
- 表：`game_results`。`id` は自動採番の主キー、`score` は必須かつ0以上、`played_at` は必須かつ省略時に現在日時。
- 実装：`database/schema.sql`、`database/practice.sql`、`scripts/database.js`、npmの `db:*` コマンド。データ・実行ファイル・接続パスワードは `.gitignore` で除外。
- 学習ガイド：`Markdown/DATABASE_STAGE2.md`。起動・停止、SQLの手入力、保存の確認、用語と会社用システムへのつながりを解説。
- 確認：追加・読み出し・スコア順と同点時の日時順、0点と既定日時、負のスコア・未入力・主キー重複の拒否、練習SQLの繰り返し、停止・再起動後の永続化、setup再実行時の記録保持。
- 検証用の行は削除済み。練習SQLはROLLBACKで取り消すため、ゲーム用の表は空の状態で引き渡し。
- PostgreSQLは検証後に停止。自分で試すときは `node scripts/database.js start`、続けて `node scripts/database.js practice` または `shell` を実行する。
- 段階3では、ブラウザからの保存・取得APIと、管理用アカウントから分けたゲーム用DB接続権限を整理する。

## 段階3：ゲームとデータベースを接続する

状態：完了（2026-10-09）

- サーバーに結果保存とランキング取得のAPIを作る。
- ゲーム終了時に保存し、過去のランキングを表示する。
- 最初の表示案：上位10件、同点は新しい日時を優先。実装時に必要なら調整する。
- 学ぶこと：API、JSON、ブラウザからの通信、入力値の確認、保存失敗時の表示。
- 到達点：ブラウザやサーバーを再起動しても記録が残る。1回のプレイが二重保存されない。
- ログインを作るまでは、自分のPC内で学習・確認する。
- API：`POST /api/results` で結果を保存、`GET /api/rankings` で上位10件を取得。整数スコア・プレイ番号・JSON形式をサーバーで確認する。
- 二重保存防止：ブラウザがプレイごとにUUIDを発行し、`play_id` の一意索引と `ON CONFLICT DO NOTHING` で同時再送も1件にする。同じ番号で異なるスコアは409で拒否。
- 再試行：未送信結果をlocalStorageに控え、再読み込み後にも送信を試す。成功後は控えを削除。ランキング本体はPostgreSQLから取得する。
- DB接続：`pg` ライブラリの最大5接続のプール。`latte_app` はSELECT・INSERTと採番だけを許可し、管理用アカウントと分ける。接続設定は `.local/postgres/app-connection.json` に置く。
- 画面：自己ベストランキング、保存状況、一覧更新・保存再試行ボタン。上位内なら今回の記録を強調表示。
- 確認：8件同時再送の重複防止、入力・サイズ・送信元の確認、上位10件と同点順、権限制限、DB停止時の503と復旧、DB・HTTPサーバー再起動後の記録保持。`node --test tests/stage3.test.js` で再確認できる。
- ブラウザ：Edgeで実時間30秒、捕獲・加点、苺のスピードアップ、自動保存、一覧更新・再読み込み、DB停止中の控えの保持、再試行後の1件保存を確認。JavaScript例外0件。
- 学習ガイド：`Markdown/DATABASE_STAGE3.md`。起動方法とAPI・JSON・パラメーター付きSQL・二重保存防止・権限・復旧の確認例を解説。
- 既存の実記録は保持し、検証で追加したプレイ番号の行だけを削除。検証用サーバーとPostgreSQLは停止して引き渡す。
- 次の段階4では、利用者番号・ログイン・所有者確認に加え、未送信の控えを利用者ごとに扱う設計を行う。

## 段階4：利用者を分ける

状態：完了（2026-10-11）

- 利用者の表を追加し、プレイ結果と利用者番号を関連付ける。
- ログインと自分の記録一覧を作る。
- 学ぶこと：表同士の関係、外部キー、認証と権限の違い、ログイン状態の管理。
- 認証には適切な既存のライブラリや仕組みを使う。
- データの所有者は、サーバーがログイン情報から判断する。
- 到達点：2人分のアカウントで、それぞれの記録が正しく保存・表示され、他人の記録を変更できない。
- 実装：`database/stage4.sql` の利用者・セッション表、結果の `user_id` 外部キーと利用者別索引。`scripts/auth.js` と認証API、ブラウザの登録・ログイン・ログアウト画面。
- 認証：Node.js標準のscrypt（N=131072・r=8・p=1）とランダムなソルトでパスワードをハッシュ化。ランダムなCookieと、ハッシュ化したセッション番号をDBで照合。有効期限12時間、HttpOnly・SameSite=Strict、Origin・CSRF確認、認証試行制限。
- 所有者：サーバーがセッションから決め、ランキングを利用者番号で絞り込む。他人のプレイ番号による再送は409で拒否し、元の記録を返さない。記録の変更・削除APIは提供しない。
- 再試行：未送信控えを利用者番号ごとのlocalStorageキーに分離。別タブでCookieが変わっても、画面の利用者番号とCSRFを確認して誤保存・別人の一覧表示を拒否する。
- 既存データ：段階3までの所有者不明の記録は利用者番号NULLのまま保持。旧形式の未送信控えも保持し、新しい利用者へ自動割当・自動送信しない。
- 起動：このPCは `auth-setup` 済み。`node scripts/database.js start`、`node scripts/server.js` を順に実行し、localhost:3000で登録・ログインして遊ぶ。新環境は `npm.cmd ci` と `node scripts/database.js auth-setup`。
- API確認：2人分の保存・取得、8件同時再送、所有者偽装・他人のプレイ番号・CSRF・Origin拒否、入力制約、誤パスワード、名前の重複・大文字小文字、ログアウト・期限切れ、認証試行制限、DB権限、停止・復旧・再起動後の永続化。更新した `tests/stage3.test.js` が成功。
- ブラウザ確認：`tests/stage4-browser.test.js` をEdgeで実行。実時間30秒のプレイ・移動・ネズミ追加、登録・ログイン・ログアウト、2人のランキング分離、通信遮断後の控え保持と再読み込み、元利用者での再送、共有Cookieが別利用者へ変わった状態での拒否・復旧を確認。JavaScript例外0件。
- 学習ガイド：`Markdown/DATABASE_STAGE4.md` に起動・確認例、認証と権限、外部キー・Cookie・セッションを解説。READMEから現在の起動手順へ案内。
- テスト用アカウントと結果だけ削除し、既存の記録を保持。検証用HTTPサーバー・Edgeは終了。公開運用・HTTPS、パスワード再設定・メール確認は今回の範囲外。
