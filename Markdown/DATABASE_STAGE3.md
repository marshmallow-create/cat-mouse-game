# 段階3：ゲームから記録を保存し、ランキングを表示する

この文書は段階3の学習記録です。現在のコードでは段階4のログインが必須です。起動・登録・利用者別ランキングの手順は [DATABASE_STAGE4.md](DATABASE_STAGE4.md) を参照してください。

今回は、ゲーム終了時のスコアをPostgreSQLへ保存し、過去の上位10件をブラウザに表示します。段階2で手入力したSQLを、Node.jsのサーバーが実行するようになりました。

## 起動方法

このPCでは依存ライブラリとAPI用データベースの準備を済ませています。PowerShellで次を実行します。

```powershell
cd C:\marshmallow\codex_projects\cat-mouse-game
node scripts/database.js start
node scripts/server.js
```

ブラウザで **http://localhost:3000** を開きます。ゲーム終了後に「記録を保存しました！」が表示され、下のランキングが更新されます。

サーバーはターミナルでCtrl + Cを押して停止します。続けて `node scripts/database.js stop` でPostgreSQLを停止できます。保存した記録は停止後も残ります。

別のPCや新しいチェックアウトで初めて用意する場合は、次を一度実行します。

```powershell
npm.cmd ci
node scripts/database.js api-setup
```

`npm.cmd ci` は `package-lock.json` に記録された組み合わせでライブラリを入れます。今回はNode.jsからPostgreSQLへ接続する `pg` を使っています。ゲーム画面はHTML・CSS・JavaScriptで動きます。

`api-setup` は段階2の準備も含め、既存の記録を残しながら新しい列・索引・ゲーム用アカウントを用意します。このPCでも再実行できます。実行ファイルやデータ、接続設定は引き続き `.local/` に保存され、Gitの対象外です。

## データの流れ

1. ブラウザで30秒のゲームが終了します。
2. ブラウザが「今回のプレイ番号とスコア」をサーバーへ送ります。
3. サーバーが入力を確認し、SQLでPostgreSQLへ保存します。
4. PostgreSQLが記録番号と日時を含む結果を返します。
5. サーバーが保存成功をブラウザへ知らせます。
6. ブラウザがランキングを要求し、サーバーが上位10件をSQLで取り出します。
7. ブラウザが受け取った記録を表に並べます。

ブラウザはデータベースのパスワードを知りません。保存・読み出しはサーバーが担当します。

## APIとJSONとは

APIは、このゲームでは「保存して」「ランキングを見せて」という要求を受ける窓口です。

| 方法とURL | 役割 |
|---|---|
| `POST /api/results` | 1回の結果を保存する |
| `GET /api/rankings` | 上位10件を取り出す |

`GET` は取得、`POST` はデータを送って処理してもらうために使います。ファイル名と同じURLでなくても、サーバーはURLに応じて処理を選べます。

データはJSONという形式でやり取りします。JavaScriptのオブジェクトに似た、項目名と値の組み合わせです。保存要求の例は次の形です。

```json
{
  "playId": "a5521b22-a401-4cee-83ba-4c983c37c1e5",
  "score": 12
}
```

日時やデータベースの記録番号は送らず、PostgreSQLが設定します。サーバーはプレイ番号の形式と、スコアが0以上の整数かを確認します。

保存が成功すると、最初の登録はHTTP **201**、同じ結果の再送は **200** を返します。入力が不正なら **400**、同じプレイ番号のスコアが異なれば **409**、データベースに接続できなければ **503** を返します。番号だけでなく、画面に表示するメッセージもJSONで返しています。

## 二重保存を防ぐ仕組み

`id` はデータベースの行の番号、`play_id` は1回のプレイにブラウザが付ける番号です。両者は役割が違います。

STARTを押すたびに新しいプレイ番号を作り、その番号は保存が成功するまで使い続けます。通信が失敗して再送しても、同じ番号です。

表の `play_id` には一意の索引を付けています。「同じ番号は1件だけ」というルールをデータベースが守るので、同時に送信された場合にも重複を防げます。

```sql
INSERT INTO game_results (play_id, score)
VALUES ($1, $2)
ON CONFLICT (play_id) DO NOTHING
RETURNING id, score, played_at;
```

`ON CONFLICT ... DO NOTHING` は、同じ番号がすでにあれば追加をしない指定です。サーバーはその後、既存の記録を読み出して返します。スコアが同じかも確認し、既存の値や日時を上書きしません。

`$1` と `$2` は値を入れる位置です。SQLの命令と入力された値を別々に渡す「パラメーター付きSQL」を使い、値を命令として解釈しないようにします。

段階2で保存した行は `play_id` がNULLのまま残ります。過去の記録はランキングに表示されます。SQLで手入力する練習も引き続き行えます。

## 保存できなかったとき

未保存の結果はブラウザの `localStorage` に一時保管します。これは通信待ちの控えで、ランキングは常にPostgreSQLから取得します。

- 失敗時には未保存の件数と「保存を再試行する」ボタンを表示します。
- 再読み込み後も同じブラウザ・同じアドレスで控えを読み出し、保存を試します。
- 保存成功後にその控えを消します。
- サーバーで保存済みなのに返事だけ届かなかった場合も、同じプレイ番号を再送するので重複しません。
- 保存とランキングの取得は別の処理です。保存に成功して一覧の取得だけ失敗した場合は、「更新する」で一覧を読み直せます。

ブラウザの保存を拒否している場合は、控えは画面を開いている間だけ保持されます。その場合、失敗メッセージに「この画面を閉じずに再試行してください」と表示します。

`localhost` と `127.0.0.1`、ポート3000と別のポートは別の保存場所になります。未保存の控えを再送するときは、元と同じアドレスを使ってください。

## データベースの権限

| アカウント | 使う場所 | 役割 |
|---|---|---|
| `latte_admin` | 準備やpsqlの学習 | 表やアカウントの管理 |
| `latte_app` | Node.jsの記録API | 結果の読み出しと追加 |

ゲーム用アカウントには必要な `SELECT`・`INSERT` と自動採番の利用権限を与えます。記録の削除・変更や、表を作る権限は与えていません。

ゲーム用の接続設定は `.local/postgres/app-connection.json` です。このファイルはブラウザへ配信せず、Gitにも入れません。

複数の要求で接続を再利用するため、`pg` の「接続プール」を使います。今回は最大5接続に制限し、待ち時間にも上限を設定しています。

## 自分で試す3つの確認

### 1．保存と取得をネットワーク画面で見る

F12で開発者ツールを開き、「ネットワーク（Network）」で `api` を検索します。1回遊ぶと `results` のPOST、その後 `rankings` のGETが見えます。要求のデータとレスポンスを開き、スコアや日時を確認してください。

ブラウザで `http://localhost:3000/api/rankings` を直接開くと、画面の表になる前のJSONも見られます。

### 2．再起動して記録が残ることを確かめる

1回遊んで保存成功を確認します。サーバーをCtrl + Cで止め、PostgreSQLも停止します。両方を再起動してページを開くと、過去の記録が表示されます。

### 3．保存失敗からの復旧を試す

ゲーム用サーバーは動かしたまま、別のPowerShellで `node scripts/database.js stop` を実行します。1回遊ぶと保存失敗と再試行ボタンが表示されます。

`node scripts/database.js start` でPostgreSQLを起動し直し、「保存を再試行する」を押します。同じプレイ番号で1件だけ保存され、ランキングが更新されます。

SQLで確認するときは、起動中に `node scripts/database.js shell` を開き、次を実行します。

```sql
SELECT id, play_id, score, played_at
FROM game_results
ORDER BY id DESC
LIMIT 10;
```

## テストの実行

API用の準備が済んだ状態で、次を実行できます。

```powershell
node --test tests/stage3.test.js
```

テストは専用のHTTPサーバーを空きポートで起動します。実際のローカルPostgreSQLにテスト用のプレイ番号の行を追加し、終了時にその行だけを削除します。途中でPostgreSQLを停止・再起動するため、普段のゲームを終了してから実行してください。

## 会社用システムへのつながりと次の段階

今回の「同じプレイ番号は1件だけ」は、業務では「送信ボタンを押し直しても同じ作業報告が二重登録されない」仕組みに応用できます。入力確認、保存失敗の表示、再試行、アプリ用アカウントの権限を分ける考え方も共通です。

現時点ではこのPCのデータベースの記録を自分用の履歴として扱います。利用者を区別するログインは段階4で追加します。その際には記録の所有者と、未送信の控えの持ち主も分けます。

今回のサーバーはスコアの形式を確認します。ブラウザから送られたスコアが実際に正しく遊んだ結果かを検証する仕組みは含みません。業務アプリでは、画面から届いた値に加えて、ログインした利用者や業務ルールをサーバーで確認することを学んでいきます。

参考：[node-postgresのパラメーター付きSQL](https://node-postgres.com/features/queries)、[接続プール](https://node-postgres.com/features/pooling)、[PostgreSQLのINSERT](https://www.postgresql.org/docs/18/sql-insert.html)、[権限の付与](https://www.postgresql.org/docs/18/sql-grant.html)。

## 実装時の確認結果（2026-10-09）

- 同じプレイ番号を8回同時に送信しても1行だけ保存され、再送時も日時が変わらないことを確認。
- 入力形式、サイズ、送信元、HTTPの方法、上位10件と同点時の並び順を確認。
- アプリ用アカウントによる変更・削除・表作成が拒否されることを確認。
- PostgreSQLとHTTPサーバーの再起動後も記録が残り、再送が重複しないことを確認。
- Edgeで30秒のゲーム、カウントダウン、移動、捕獲、苺のスピードアップ、自動保存、ランキング更新を確認。
- データベース停止時の保存失敗、再読み込み後の控えの保持、復旧後の再試行による1件保存を確認。
- ブラウザ確認中のJavaScript例外は0件。停止中のAPIの503は、失敗表示を確かめるために意図的に発生させました。
- 既存の記録を保持し、テストで追加した行だけを削除。検証用サーバーとPostgreSQLは停止しています。
